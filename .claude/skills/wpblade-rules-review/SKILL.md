# 規約レビュー（コミット前ゲート）

変更内容を `.claude/rules/` の規約と突き合わせ、違反を解消してからコミットを許可する。照合は自分でやらず **rules-reviewer サブエージェント**に委譲する（実装した本人の文脈はレビューの盲点になるため。自分でルールを読み直して済ませるのは禁止）。

## 前提

- git リポジトリであること（差分は `HEAD` 基準）
- レビュー対象は「HEAD との差分 + 未追跡ファイル」。コミット直前＝**他の作業がすべて終わった後**に実行する（レビュー後にファイルを変更するとマーカーが失効し、再レビューが必要になる）

## 作業手順

1. **変更ファイルを列挙する**

   ```bash
   git diff HEAD --name-only; git ls-files --others --exclude-standard
   ```

2. **各ルールの `paths` frontmatter を確認し、担当を割り当てる**

   ```bash
   for f in $(find .claude/rules -name '*.md' | sort); do echo "== $f"; sed -n '2,/^---$/p' "$f" | sed '$d'; done
   ```

   - `paths` の glob にマッチする変更ファイルがあるルール → 照合対象
   - `paths` の無いルール（`architecture.md` / `security.md` 等）→ 変更が1つでもあれば常に照合対象
   - マッチする変更が1つも無いルールはスキップ（レビュアーを起動しない）

3. **rules-reviewer サブエージェントを並列起動する**（Agent ツール。1呼び出し = ルールファイル1つ）
   - プロンプトに渡すもの: ①ルールファイルパス ②そのルールが担当する変更ファイル一覧 ③「未追跡ファイルは全文がレビュー対象」の注記
   - 対象ルールが複数あれば**1メッセージでまとめて並列起動**する
   - **security.md だけは独立に2体起動する。ただし同じ指示を2回投げない**（同一のチェックリストでは誤りが相関し、2倍のコストで検出力がほとんど上がらない）。次の**異なる観点**を1体ずつに割り当て、どちらかが fail とした項目は fail として扱う:

     | 観点             | 追加で渡す指示                                                                                                                                                                                                                                                                                                                                                  |
     | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
     | **経路追跡**     | 「変更範囲に現れる**ユーザー入力の入口を全部列挙**し（REST のリクエストボディ、`$_GET` / `$_POST`、投稿メタ、カスタムフィールド、URL パラメータ）、各々が最終的にどこへ出力されるか（HTML / 属性 / URL / インライン JS / メールヘッダー / SQL）を追跡せよ。**出力先の文脈ごとに必要な処理がされているか**を報告せよ。チェックリストに無い経路でも報告すること」 |
     | **パターン照合** | 「security.md の『判断が割れる箇所』の全項目と変更内容を1項目ずつ突き合わせよ。**該当なしと判断した項目もその理由を書く**こと」                                                                                                                                                                                                                                 |

     経路追跡側は「security.md に載っていない新しい形」を、パターン照合側は「既知の落とし穴」を担当する。両方 pass のときだけ pass。

4. **結果を集約し、違反を修正する**
   - **Critical / Warning は修正する**。ただし修正がユーザーの意図（仕様・文言・デザイン）に関わる場合は独断せず確認する
   - **Info は修正せず報告のみ**（規約側が曖昧なものは規約更新の候補として報告に含める）
   - レビュアーの fail 報告を鵜呑みにしない。**修正前にルール原文と該当行を自分でも確認**し、偽陽性なら修正せずその判断を記録する

5. **修正したら再レビュー**
   - 修正したファイルを担当するルールのレビュアーだけ再起動する（全件やり直さない）
   - 「修正 → 再レビュー」は**最大3周**。3周で収束しなければ止めて、残違反と経緯をユーザーに報告し判断を仰ぐ

6. **全違反解消でゲートのマーカーを記録する**

   ```bash
   .claude/hooks/rules-review-gate.sh --pass
   ```

   これで `git commit` が hook を通過できるようになる。**違反が残った状態で `--pass` を実行しない**こと。

7. **ユーザーへ報告する**: 照合したルール × 変更ファイルのマトリクス、fail → 修正の一覧、Info（未修正）の一覧、偽陽性として棄却した報告

## 規約

- マーカー記録（`--pass`）は違反ゼロ（Critical / Warning 解消済み）のときだけ
- `SKIP_RULES_REVIEW=1` によるゲートの素通しは**人間がコマンドを打つときの緊急用**。Claude が自発的に付けてはならない
- レビュアーは読み取り専用。修正はこのスキル（メインセッション）側で行う

## 注意

- マーカーは**作業ツリーの内容ハッシュ**。レビュー後にコミットを何回に分けても失効しないが、ファイルを変更すると失効し再レビューが必要になる（分割コミットの手順は `wpblade-ship` スキル）
- `.claude/rules/` 自体を変更した場合も通常どおりレビューを回す（規約と参照実装のズレはレビュアーが Info として拾う）
- レビューで見逃しがあとから見つかったら、**違反例としてルールファイルに before/after を追記**する（few-shot が次回以降の検出率を上げる。lint ルールを書く代わりに違反例を書くのがこの運用のメンテナンス）

## 完了チェックリスト

- [ ] 変更ファイル全部がいずれかのレビュアーに割り当てられた（どのルールにもマッチしないファイルは「対象規約なし」として報告に明記）
- [ ] Critical / Warning がゼロ
- [ ] `rules-review-gate.sh --pass` を実行した
- [ ] 照合結果マトリクスをユーザーに報告した

# 出荷（分割コミット + PR 説明文）

実装が終わってから PR を出すまでの定型手順。**レビュー → 分割コミット → PR 用生 md** の順で行う。push と PR 作成そのものはユーザーが明示的に指示したときだけ。

## 前提

- 実装・動作確認が完了していること（このスキルは仕上げ工程。実装の続きはしない）
- コミットは規約レビューゲートで守られている。**先に `wpblade-rules-review` スキルを完了させる**こと（マーカーは作業ツリーの内容ハッシュなので、レビュー後にコミットを何回に分けても失効しない。ファイルを変更すると失効する）

## 作業手順

### 1. 変更全体を把握する

```bash
git status; git diff HEAD --stat
```

### 2. 検証コマンドを通し、vendor/ を本番状態に戻す

変更の種類に応じて次を実行し、すべて通ることを確認する。

| 変更したもの                          | 実行するコマンド                                                                                                                                                          |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app/` `includes/` テーマ直下 `*.php` | `composer test`                                                                                                                                                           |
| `resources/ts/`                       | `npm run typecheck`（**`npm run build` は型エラーを検出しない**。Vite は esbuild で型注釈を落とすだけで検査しないため、明示的に実行しないと型エラーがそのまま出荷される） |
| `resources/` 全般（js / ts / scss）   | `npm run build`                                                                                                                                                           |

そのうえで vendor/ を本番状態（dev 依存なし）に戻す:

```bash
composer install --no-dev
```

コミットされる vendor/ は常に `--no-dev` 状態を保つ規約（[CLAUDE.md](../../../CLAUDE.md) 参照）。**この戻しは必ず規約レビューより前に行う**（レビューマーカーは作業ツリーの内容ハッシュのため、レビュー後に vendor/ が変わるとマーカーが失効してコミットがブロックされる）。

### 3. 規約レビューを完了させる

`wpblade-rules-review` スキルを実行し、違反解消 → マーカー記録まで済ませる（未実施のままコミットするとゲートにブロックされる）。

### 4. 意味のある単位に分割してコミットする

**1コミット = 1つの意図**。次の基準で分ける:

- 単独で読める・単独で revert できる粒度（例: 「機能本体」「その機能の設定追加」「無関係のリファクタ」「ドキュメント更新」は別コミット）
- 動く状態を保つ順序で積む（後のコミットが無いとビルドが壊れる分け方をしない）
- 混ざった diff はファイル単位の `git add <path>`、同一ファイル内で混ざっていれば `git add -p` で分離
- 分け方に複数の解釈があり得るときは、コミットする前に分割案を1〜3行で提示して確認する

**コミットメッセージ規約**（既存ログに準拠）:

```
type(scope): 日本語で変更の要約
```

- `type`: `feat`（機能追加）/ `fix`（不具合修正）/ `refactor`（挙動を変えない整理）/ `chore`（画像差し替え・設定・雑務）/ `docs`（ドキュメント）/ `style`（整形のみ）
- `scope`: 機能・領域名（例: `trial` / `lp` / `front-page` / `rules`）
- 例: `feat(trial): 体験予約フォームに復帰URL・完了後導線を追加`

### 5. PR 説明文の生 Markdown を出力する

下のテンプレートに沿って組み立て、**コードフェンス（````markdown`）で囲った生テキスト**として出力する（ユーザーが GitHub にそのまま貼る）。該当のないセクションは削る。**diff に無いことを書かない**（動作確認は実際にやったことだけを書く）。

```markdown
## 概要

（何を・なぜ。1〜3文。スコープ外にしたことがあれば明記）

## 主な変更

- **（領域）**: （変更内容。クラス名・ファイル名は具体的に）
- ...

## リリース手順

（マージ＝自動デプロイ等の注意があるときのみ。管理画面での作業・環境変数・外部依存の
段取りを、マージ前にやるべき順で番号付きリストにする）

## 動作確認

- （ローカル / ステージングで実際に確認したこと。検証コマンドの通過状況もここに）

## 既知の残課題（本PRでは未対応）

- （レビューで Warning 止まりにしたもの、スコープ外に切ったもの）
```

末尾に次のフッターを付ける:

```markdown
🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

### 6. 報告して終了

コミット一覧（`git log --oneline`）と PR 用 md を提示して終わる。**push・`gh pr create` はユーザーが指示したときだけ**行う（PR 作成を頼まれたら、生成済みの md を `--body-file` でそのまま使う）。

## 注意

- コミット後に修正が発生したら、ファイル変更でマーカーが失効するので再レビュー（`wpblade-rules-review`）からやり直す
- 出荷後に開発を再開してテストを回すときは `composer install` で dev 依存を戻す（次回出荷時にまた `--no-dev` に戻す）
- `SKIP_RULES_REVIEW=1` を自発的に使わない（ゲートの規約どおり）
- PR タイトルはコミット規約と同じ `type(scope): 要約` 形式（ブランチの主目的で1つ選ぶ）

## 完了チェックリスト

- [ ] 変更範囲に対応する検証コマンド（`composer test` / `npm run typecheck` / `npm run build`）が通り、vendor/ が `--no-dev` 状態に戻っている
- [ ] `wpblade-rules-review` が完了している（Critical / Warning ゼロ）
- [ ] コミットが意図単位に分かれ、メッセージが `type(scope): 日本語` 形式
- [ ] PR 用生 md を出力した（実際にやった動作確認だけを記載）
- [ ] push / PR 作成は指示があった場合のみ実施した
